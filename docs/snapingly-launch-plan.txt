Core Assumptions
================

1. Brand/domain:
   - Product name: Snapingly.
   - Target domain: snapingly.com, unless you buy a different domain.
   - Existing copy that says Screenshot Beautifier should eventually become
     Snapingly.

2. Pricing:
   - Free plan: account required at export time; limited to 10 watermarked
     exports per calendar month.
   - Pro monthly: 4.99 USD/month.
   - Pro yearly: 39 USD/year.
   - Founder monthly: 2.99 USD/month for the first 100 paying users.
   - Founder yearly: 19 USD/year for the first 100 paying users.
   - Assumption: founder pricing is permanent while that subscription remains
     active. If you want "first billing period only" instead, change the Dodo
     product/discount setup before implementation.

3. Auth:
   - Supabase Auth.
   - Google sign-in.
   - Email OTP sign-in. Prefer passwordless OTP/magic code over passwords for
     launch because it lowers support and password security scope.
   - Sign-up/sign-in should appear when the user tries to export, not before
     editing.

4. Payments:
   - Dodo Payments is the payment processor.
   - Dodo hosted checkout is preferred for launch.
   - Dodo webhooks are the source of truth for paid access.
   - The Dodo return URL is not trusted for activating a subscription.

5. Privacy:
   - Current app promise is local-only screenshot handling.
   - For the recommended launch version, screenshots still do not get uploaded
     or stored. Supabase stores account, subscription, quota, and export metadata
     only.
   - If you later choose server-side rendering for stronger DRM, the privacy
     copy must change because the image must be sent to a server during export.

6. Architecture:
   - Keep the existing Next.js App Router app.
   - Use Next.js route handlers as the backend for checkout creation, billing
     portal creation, export authorization, and webhooks.
   - Use Supabase Postgres as the database.
   - Do not add a separate MERN backend for launch.


Important Pushback: MERN Is Not The Best Fit Here
=================================================

You mentioned MERN for the backend. For this app, MERN would add a second backend
and a second database even though Supabase already gives you Postgres, auth, JWTs,
RLS, migrations, and secure server-side access.

Recommended launch architecture:

Browser:
  - Upload/edit preview remains client-side.
  - Export UI asks server for authorization before producing PNG.
  - Free users see and export with Snapingly watermark.
  - Pro users export without watermark and can use 4x/pro features.

Next.js app:
  - Server Components and Client Components for UI.
  - Route handlers under src/app/api/* for backend calls.
  - Auth callback route for Supabase OAuth/OTP.
  - Webhook route for Dodo.

Supabase:
  - Auth users.
  - Postgres tables for profiles, subscriptions, quota, founder slots, checkout
    sessions, export events, and webhook events.
  - RLS enabled on exposed tables.
  - Service role key used only inside server routes or secured server functions.

Dodo Payments:
  - Hosted checkout sessions.
  - Subscription lifecycle webhooks.
  - Customer portal for cancellation, invoice access, and payment method updates.

Only consider a separate Node/Express backend later if:
  - You need long-running server-side image rendering workers.
  - You outgrow serverless function limits.
  - You need a dedicated queue/worker setup.

Do not use MongoDB unless there is a real document-storage need. User/account and
billing state is relational and fits Postgres better.


Critical Security Truth About Frontend Export
=============================================

Because the current export is generated in the browser with html-to-image, no
backend call can make watermark removal cryptographically impossible.

What a backend can enforce:
  - Whether the official UI enables 4x export.
  - Whether the official UI should include a watermark.
  - Whether a user has monthly free quota remaining.
  - Whether paid status is active.
  - Whether a premium feature can be exported.
  - Server-side audit records for normal users.

What a backend cannot fully prevent if screenshots stay local:
  - A technical user modifying local JavaScript in DevTools.
  - A user cloning the app and removing the watermark.
  - A user manually recreating a similar export outside your app.

Recommended launch decision:
  - Use server-authorized client export for v1 paid launch.
  - Accept that this is a product gate, not DRM.
  - Keep the strong privacy promise: screenshots stay in the browser.
  - Add server-side rendering only if abuse becomes real enough to justify the
    extra infrastructure and weaker privacy story.

High-security alternative:
  - Add /api/export/render.
  - Upload the screenshot blob and design settings at export time.
  - Render the PNG server-side.
  - Return the final PNG.
  - Delete temporary files immediately.
  - Never persist the uploaded screenshot.
  - Update privacy policy and in-app copy to say exports are processed
    transiently on the server.
  - This is more complex and may require a browser renderer/worker, not just a
    simple Supabase Edge Function.


Recommended Free vs Pro Packaging
=================================

Free plan:
  - Account required only when trying to export.
  - 10 exports per month.
  - Watermark always included in exported artwork.
  - Watermark visible in preview so the user is not surprised.
  - Export scale limited to 1x and 2x.
  - 4x visible but marked Pro.
  - Premium quick styles/features visible but marked Pro.
  - If a Pro feature is used, free export should be blocked with a clear upgrade
    modal rather than silently changing the design.

Pro plan:
  - No watermark.
  - 1x, 2x, and 4x export.
  - Premium quick styles allowed.
  - Premium visual effects allowed.
  - Higher or unlimited monthly exports. Suggested launch position:
    "Unlimited exports for normal use" with a fair-use clause in Terms.

Features to mark as Pro:
  - 4x export.
  - Remove watermark.
  - Premium quick style pack.
  - Premium background pack.
  - Premium text effect pack.

Features to keep free:
  - Upload/paste/edit.
  - Core quick styles.
  - Canvas presets.
  - Browser frame.
  - Basic text overlays.
  - 1x and 2x export with watermark.

Why this packaging works:
  - Users can feel the value before payment.
  - The free tier markets the product through watermark.
  - Paid value is clear: remove watermark, unlock high-res, unlock premium
    polish.
  - The app stays simple and does not become a heavy design suite.


User Flow
=========

1. User lands on snapingly.com.
2. User clicks editor CTA.
3. User uploads/pastes a screenshot.
4. User edits freely without an account.
5. User chooses export settings.
6. User clicks Download PNG or Copy PNG.
7. If not signed in:
   - Open auth modal.
   - Offer Google sign-in.
   - Offer email OTP.
   - Keep current editor state in memory.
   - After auth success, resume export flow.
8. If signed in free:
   - Server checks free quota.
   - Server checks selected export scale and premium features.
   - If allowed, return "watermark required" export authorization.
   - Client exports with Snapingly watermark.
9. If signed in Pro:
   - Server checks active subscription from Supabase.
   - If active, return "no watermark" export authorization.
   - Client exports at selected scale, including 4x.
10. If user needs Pro:
   - Show upgrade modal.
   - Monthly, yearly, and founder pricing if founder seats remain.
   - User chooses plan.
   - Server creates Dodo checkout session.
   - Browser redirects to Dodo hosted checkout.
11. After checkout:
   - User returns to /billing/return.
   - Return page shows "confirming payment".
   - App polls /api/billing/status.
   - Dodo webhook updates subscription state.
   - User gets Pro export access only after webhook-confirmed status.


Watermark Rules
===============

Watermark brand:
  - Text: Snapingly
  - Optional longer text: Made with Snapingly
  - Placement: frame/artwork right bottom.
  - Opacity: 50%.
  - Must be visible in preview for free users.
  - Must be included in export for free users.
  - Must not cover important screenshot content more than necessary.

Design:
  - Small, tasteful, premium.
  - White or black depending on background contrast.
  - 50% opacity, but preserve minimum readability.
  - Position inside final artwork, not outside the exported canvas.
  - Avoid making it look cheap.

Implementation idea:
  - Add a Watermark component used by CanvasArtwork.
  - CanvasArtwork already has mode="preview" and mode="export"; use the same
    source of truth for both.
  - Watermark visibility comes from entitlement/export authorization state, not
    arbitrary local UI state.


Export Authorization Design
===========================

Recommended endpoints:

1. POST /api/export/prepare
   Purpose:
     - Validate authenticated user.
     - Check subscription status.
     - Check monthly free quota.
     - Check requested export scale.
     - Check whether selected design includes Pro-only features.
     - Create an export attempt record.
     - Return export rules to the client.

   Request body:
     - requestedScale: 1 | 2 | 4
     - action: "download" | "copy"
     - usedFeatureKeys: string[]
     - canvasPresetId
     - backgroundPresetId
     - browserFrameEnabled
     - imageCount
     - clientExportId: random UUID generated client-side for idempotency

   Do not send:
     - Screenshot file.
     - Object URL.
     - Base64 image.

   Response:
     - exportAttemptId
     - allowed: boolean
     - reason: null | "auth_required" | "quota_exceeded" | "pro_required"
     - entitlement: "free" | "pro"
     - requiresWatermark: boolean
     - watermarkText: "Snapingly"
     - maxScale: 1 | 2 | 4
     - blockedFeatureKeys: string[]
     - quota: { used, limit, periodStart, periodEnd }

2. POST /api/export/complete
   Purpose:
     - Mark the prepared export attempt as succeeded or failed.
     - Store non-sensitive export metadata.

   Request body:
     - exportAttemptId
     - status: "succeeded" | "failed"
     - failureCode if failed
     - outputScale
     - outputPixelWidth
     - outputPixelHeight

3. Optional future endpoint: POST /api/export/render
   Purpose:
     - Stronger enforcement through server-side PNG generation.
     - Only add this if you accept temporary image upload and more backend
       complexity.

Quota counting:
  - For free users, count quota at prepare time once an export attempt is
    allowed. This prevents users from preparing infinite exports and never
    calling complete.
  - Allow retry of the same exportAttemptId if the client export fails due to a
    recoverable browser error.
  - Store only metadata, not images.

Database Schema Plan
====================

Use Supabase migrations. Do not hand-edit production DB tables randomly from the
dashboard after launch.

Recommended tables:

1. public.profiles
   Purpose:
     - Public app profile linked to auth.users.

   Columns:
     - id uuid primary key references auth.users(id) on delete cascade
     - email text not null
     - full_name text
     - avatar_url text
     - dodo_customer_id text unique
     - founder_customer boolean default false
     - created_at timestamptz default now()
     - updated_at timestamptz default now()

   RLS:
     - User can select own profile.
     - User can update safe own fields only if needed.
     - Server/service role can manage billing fields.

2. public.subscriptions
   Purpose:
     - Local mirror of Dodo subscription state.

   Columns:
     - id uuid primary key default gen_random_uuid()
     - user_id uuid not null references auth.users(id) on delete cascade
     - dodo_subscription_id text unique not null
     - dodo_customer_id text
     - dodo_product_id text
     - plan_key text not null
       Values: "monthly", "yearly", "founder_monthly", "founder_yearly"
     - status text not null
       Values mirror Dodo, for example: "active", "on_hold", "cancelled",
       "expired", "failed"
     - current_period_start timestamptz
     - current_period_end timestamptz
     - cancel_at_period_end boolean default false
     - cancelled_at timestamptz
     - cancellation_feedback text
     - cancellation_comment text
     - raw_payload jsonb
     - created_at timestamptz default now()
     - updated_at timestamptz default now()

   Indexes:
     - unique dodo_subscription_id
     - index user_id
     - index status
     - index current_period_end

   RLS:
     - User can select own subscription rows.
     - User cannot insert/update/delete directly.
     - Webhook/server updates through service role only.

3. public.checkout_sessions
   Purpose:
     - Track Dodo checkout sessions created by the app.

   Columns:
     - id uuid primary key default gen_random_uuid()
     - user_id uuid not null references auth.users(id) on delete cascade
     - dodo_session_id text unique
     - plan_key text not null
     - dodo_product_id text not null
     - checkout_url text
     - founder_offer boolean default false
     - status text not null default "created"
       Values: "created", "returned", "completed", "expired", "cancelled"
     - metadata jsonb
     - created_at timestamptz default now()
     - updated_at timestamptz default now()

   RLS:
     - User can select own checkout sessions if needed.
     - User cannot insert/update/delete directly.

4. public.founder_slots
   Purpose:
     - Enforce first 100 founder users server-side.

   Suggested shape:
     - slot_number integer primary key check slot_number between 1 and 100
     - status text not null default "available"
       Values: "available", "reserved", "claimed", "released"
     - reserved_by uuid references auth.users(id)
     - reserved_at timestamptz
     - reservation_expires_at timestamptz
     - claimed_by uuid references auth.users(id)
     - claimed_at timestamptz
     - dodo_checkout_session_id text
     - dodo_subscription_id text

   How it works:
     - Pre-create 100 rows.
     - When user starts founder checkout, reserve the lowest available slot for
       30 minutes.
     - If checkout succeeds, webhook marks slot claimed.
     - If checkout is abandoned, an expired reservation can be released.

   RLS:
     - Users can only read founder availability through a server endpoint or a
       safe view.
     - Direct writes disabled for client.

5. public.export_attempts
   Purpose:
     - Track export authorization and quota usage.

   Columns:
     - id uuid primary key default gen_random_uuid()
     - user_id uuid not null references auth.users(id) on delete cascade
     - client_export_id text not null
     - entitlement text not null
       Values: "free", "pro"
     - action text not null
       Values: "download", "copy"
     - requested_scale integer not null
     - allowed_scale integer not null
     - requires_watermark boolean not null
     - used_feature_keys text[] default '{}'
     - blocked_feature_keys text[] default '{}'
     - status text not null default "prepared"
       Values: "prepared", "succeeded", "failed"
     - failure_code text
     - output_pixel_width integer
     - output_pixel_height integer
     - period_start date not null
     - period_end date not null
     - created_at timestamptz default now()
     - completed_at timestamptz

   Constraints/indexes:
     - unique(user_id, client_export_id)
     - index(user_id, period_start)
     - index(created_at)

   RLS:
     - User can select own export attempts.
     - User cannot insert/update directly.

6. public.export_usage_months
   Purpose:
     - Fast monthly quota lookup.

   Columns:
     - user_id uuid not null references auth.users(id) on delete cascade
     - period_start date not null
     - period_end date not null
     - free_watermarked_exports integer not null default 0
     - pro_exports integer not null default 0
     - updated_at timestamptz default now()
     - primary key(user_id, period_start)

   RLS:
     - User can select own row.
     - Server writes only.

7. public.dodo_webhook_events
   Purpose:
     - Idempotency and audit log for Dodo webhooks.

   Columns:
     - webhook_id text primary key
     - event_type text not null
     - dodo_object_id text
     - processing_status text not null
       Values: "received", "processed", "failed", "ignored"
     - payload jsonb not null
     - error_message text
     - received_at timestamptz default now()
     - processed_at timestamptz

   RLS:
     - No client access.
     - Service role only.

8. public.billing_entitlements_view or server helper function
   Purpose:
     - Compute whether the user is free or Pro.

   Logic:
     - Pro if latest relevant subscription is active and current_period_end is
       null or in the future.
     - Not Pro if status is on_hold, cancelled, expired, or failed.
     - If cancel_at_period_end is true but still active and period end is in
       the future, keep access until period end.


RLS And Database Security Rules
===============================

Rules:
  - Enable RLS on every table in public.
  - Client can read only its own rows where auth.uid() = user_id.
  - Client cannot directly update billing state, quota, founder slots, webhook
    events, or subscription rows.
  - Server route handlers use service role only when needed.
  - Never expose SUPABASE_SERVICE_ROLE_KEY in browser code.
  - Never put billing authorization in raw_user_meta_data because users can
    modify user metadata.
  - If using JWT custom claims later, store authorization-relevant claims in
    app_metadata only, and remember JWT claims are not always immediately fresh.
  - For launch, prefer database lookup of subscription status in server routes
    over relying only on JWT claims.

Suggested policies:
  - profiles select: auth.uid() = id
  - profiles update: auth.uid() = id, but only for safe profile fields if needed.
  - subscriptions select: auth.uid() = user_id
  - checkout_sessions select: auth.uid() = user_id
  - export_attempts select: auth.uid() = user_id
  - export_usage_months select: auth.uid() = user_id
  - No client insert/update/delete policies for billing/quota/webhook tables.

Use DB constraints as security too:
  - Unique Dodo IDs.
  - Check allowed status values.
  - Foreign keys to auth.users.
  - Not-null on critical fields.
  - Idempotency unique keys for webhook_id and client_export_id.


Dodo Payments Plan
==================

Dodo setup:
  - Create Dodo merchant account and complete account verification before launch.
  - Create subscription products:
    1. Snapingly Pro Monthly - 4.99 USD/month.
    2. Snapingly Pro Yearly - 39 USD/year.
    3. Snapingly Founder Monthly - 2.99 USD/month.
    4. Snapingly Founder Yearly - 19 USD/year.

Why separate founder products:
  - It avoids relying on discount-code edge cases.
  - The server can choose founder products only while founder slots remain.
  - It clearly preserves founder pricing for the life of the subscription.

Alternative:
  - Use Dodo discount codes if you want discounts instead of separate products.
  - Before coding, verify whether Dodo currently allows pre-applying discount
    codes in checkout sessions for your exact checkout flow.

Dodo checkout:
  - Use hosted checkout sessions.
  - Create checkout session only from the server.
  - Pass product_cart with the selected Dodo product ID.
  - Pass customer email/name from Supabase user/profile.
  - Pass metadata:
    - supabase_user_id
    - plan_key
    - founder_slot_number if reserved
    - app: "snapingly"
  - return_url: https://snapingly.com/billing/return
  - cancel_url: https://snapingly.com/editor?billing=cancelled

Dodo webhooks:
  - Endpoint: POST /api/webhooks/dodo
  - Verify webhook signature before parsing/trusting the payload.
  - Store webhook_id for idempotency.
  - Process subscription events:
    - subscription.active
    - subscription.updated
    - subscription.on_hold
    - subscription.renewed
    - subscription.plan_changed
    - subscription.cancelled
    - subscription.failed
    - subscription.expired
  - Update local subscriptions table.
  - Mark founder slot claimed when subscription becomes active.
  - Release founder reservation on failed/expired checkout if applicable.

Important:
  - Do not trust frontend "payment successful" query params.
  - Do not trust Dodo return URL alone.
  - Only webhook-confirmed subscription state grants Pro access.
  - Webhook processing must be idempotent because payment providers can retry
    events.

Customer portal:
  - Add /account or account menu item after launch.
  - Button: Manage billing.
  - Server endpoint creates Dodo customer portal session or sends user to Dodo
    portal.
  - Customers can cancel, update payment method, and view invoices through Dodo.

Security Checklist
==================

Auth/session:
  - Use Supabase SSR helpers for Next.js.
  - Server routes must read the authenticated user from Supabase session/JWT.
  - Never accept user_id from the browser as authority.
  - Never use raw_user_meta_data for entitlements.
  - Keep sessions in secure cookies through Supabase SSR flow.

Database:
  - RLS enabled on every exposed table.
  - No direct client write access to subscriptions, quotas, founder slots, or
    webhook events.
  - Use constraints and unique indexes for billing IDs and idempotency.
  - Use migrations, not ad hoc production dashboard edits.
  - Back up production database.
  - Enable Supabase Security Advisor checks before launch.

Payments:
  - Dodo API key server-only.
  - Webhook secret server-only.
  - Verify webhook signature.
  - Process webhooks idempotently.
  - Trust webhook state, not redirect query params.
  - Log failed webhook processing and retry safely.

API:
  - Same-origin calls for app APIs.
  - Validate all request bodies.
  - Rate-limit sensitive routes:
    - /api/billing/checkout
    - /api/export/prepare
    - /api/export/complete
  - Return generic errors where detailed errors could leak internals.
  - Do not log secrets.
  - Do not log screenshot image data.

Frontend:
  - Treat frontend gating as UX only.
  - Server remains source of truth for quota and subscription.
  - Keep watermark in CanvasArtwork, the export source of truth.
  - Do not add auth/payments state to localStorage.
  - Theme localStorage is okay because it is not sensitive.

Headers:
  - Add production security headers:
    - Strict-Transport-Security
    - X-Content-Type-Options: nosniff
    - Referrer-Policy
    - Permissions-Policy
    - Content-Security-Policy
  - CSP must allow only needed origins:
    - self
    - Supabase project URL
    - Dodo checkout/customer portal
    - Google OAuth/accounts where needed
  - Test CSP carefully because auth/payment redirects can break if too strict.

Secrets:
  - Use Vercel/Supabase secret managers.
  - Never commit .env files.
  - Rotate secrets if accidentally exposed.
  - Separate test and live Dodo keys.
  - Separate development and production Supabase projects if feasible.

Abuse/fraud:
  - Free export quota requires account.
  - Quota is per Supabase user per month.
  - Consider rate limiting by user ID and IP hash.
  - Do not collect more personal data than needed.
  - For suspicious abuse, block account server-side by adding a profile status
    field later.

Final Recommendation
====================

Launch with:
  - Next.js route-handler backend, not MERN.
  - Supabase Auth and Postgres.
  - Dodo hosted checkout and webhooks.
  - Free account-required exports with watermark.
  - 10 free exports/month.
  - Pro no-watermark and 4x export.
  - Founder pricing through separate Dodo products and a server-enforced 100-slot
    reservation system.
  - Privacy-preserving client-side export for v1.
  - Clear acceptance that client-side export gating is not unbreakable DRM.

This gives you the best launch balance: fast to build, simple to operate, good
privacy story, low backend complexity, and strong enough monetization controls
for normal users.
