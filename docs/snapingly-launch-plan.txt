Purpose
=======

This is the operating plan for taking the current local-only Screenshot
Beautifier app live as Snapingly with a free tier, paid entitlements, watermark
gating, Supabase Auth/Postgres, and Dodo Payments.

This plan is intentionally staged. The first executable milestone must not
pretend Supabase or Dodo are already connected. Build the local contracts and
watermark behavior first, then connect real auth, database, and payments later.


Current Decisions
=================

1. Brand:
   - Product name: Snapingly.
   - Target domain: snapingly.com unless a different domain is purchased.
   - Existing Screenshot Beautifier copy should eventually become Snapingly.

2. Privacy:
   - Screenshots stay local in the browser.
   - Never send screenshot files, blobs, base64, object URLs, rendered PNGs, or
     image data to Supabase, Dodo, route handlers, webhooks, logs, or third
     parties.
   - Supabase may store account, subscription, quota, export authorization, and
     non-sensitive export metadata only.

3. Monetization:
   - Free and anonymous users are treated as the free plan.
   - Free exports include a bottom-right "Made with Snapingly" watermark.
   - Paid users can remove the watermark later.
   - Pricing is TBD. Do not hardcode prices yet.
   - Exact paid feature packaging is TBD. Only one paid entitlement is locked
     for now: removing the Snapingly watermark.

4. Backend:
   - Use Next.js App Router route handlers as the backend layer.
   - Use Supabase Auth and Supabase Postgres when connected later.
   - Use Dodo hosted checkout and webhooks when connected later.
   - Do not add MERN, MongoDB, a separate Express API, analytics, telemetry, AI
     APIs, saved projects, share links, GIF export, video export, Three.js, or
     WebGL for this launch path.


Important Backend Direction
===========================

Do not build a MERN backend for launch. Supabase already provides Auth,
Postgres, RLS, migrations, service-role access, and server-aware sessions. A
separate Node/Express/Mongo stack would add operational work without improving
the first paid launch.

Recommended launch architecture:

Browser:
  - Upload, edit, preview, and PNG generation remain client-side.
  - Local/mock export authorization is used until Supabase is connected.
  - Free entitlement shows and exports the Snapingly watermark.
  - No image payload leaves the browser.

Next.js:
  - Server Components and Client Components for UI.
  - Future route handlers under src/app/api/* for export authorization, billing
    status, checkout, portal, and Dodo webhooks.
  - Server routes validate the authenticated user from Supabase when auth is
    connected.

Supabase, later:
  - Auth users.
  - Postgres tables for profiles, subscriptions, checkout sessions, export
    attempts, monthly usage, and webhook events.
  - RLS enabled on public tables.
  - Service role key used only in server routes.

Dodo Payments, later:
  - Hosted checkout sessions.
  - Subscription lifecycle webhooks are the source of truth for paid access.
  - Customer portal for cancellation, invoices, and payment method updates.


Frontend Export Security Reality
================================

The current export is generated in the browser with html-to-image. That is the
right privacy tradeoff for launch, but it is not unbreakable DRM.

What the backend can enforce for normal users:
  - Whether the official UI includes the watermark.
  - Whether a user has monthly quota remaining after auth is connected.
  - Whether a user has webhook-confirmed paid access.
  - Whether selected feature keys are allowed for the current entitlement.
  - Non-sensitive export audit records.

What the backend cannot fully prevent while screenshots stay local:
  - A technical user changing local JavaScript.
  - A cloned app with the watermark removed.
  - A user recreating a similar visual elsewhere.

Launch decision:
  - Accept product-level gating, not DRM.
  - Keep the strong local-only privacy story.
  - Consider server-side rendering only later if abuse justifies sending images
    transiently to a server and changing the privacy copy.

  - entitlement: "free" | "pro"

  - watermarkText: "Made with Snapingly" | null

  - blockedFeatureKeys: FeatureKey[]

  - Allow export.
  - Require watermark.
  - Do not perform quota checks yet.
  - Do not require auth yet.


Watermark Rules
===============

Text:
  - Made with Snapingly

Placement:
  - Bottom right inside the final artwork canvas.
  - Never outside the exported canvas.
  - Keep clear of the canvas edge with responsive padding.

Visual style:
  - Small, tasteful, and premium.
  - Semi-transparent, but readable.
  - Use a subtle pill/backdrop treatment so it remains visible across light,
    dark, gradient, and image-blur backgrounds.
  - Do not let it look like an editing control.

Behavior:
  - Show in preview for free/local entitlement.
  - Include in hidden export renderer for free/local entitlement.
  - Paid users can remove it later through "watermark.remove".
  - Do not let quick styles remove, replace, upload, persist, or rewrite the
    watermark.


Future API Contracts
====================

Add these only when Supabase/Dodo setup is ready.

POST /api/export/prepare
  Purpose:
    - Validate Supabase-authenticated user.
    - Check subscription status.
    - Check monthly free quota.
    - Check requested export scale and used feature keys.
    - Create an export attempt record.
    - Return export rules.

  Request body:
    - requestedScale
    - action: "download" | "copy"
    - usedFeatureKeys
    - clientExportId
    - non-sensitive design identifiers, if needed

  Never send:
    - Screenshot file.
    - Blob.
    - Object URL.
    - Base64 image.
    - Rendered PNG.

POST /api/export/complete
  Purpose:
    - Mark the prepared export attempt as succeeded or failed.
    - Store non-sensitive output metadata such as scale and pixel size.

GET /api/billing/status
  Purpose:
    - Return current plan, paid access, quota, and whether watermark removal is
      allowed.

POST /api/billing/checkout
  Purpose:
    - Create a Dodo hosted checkout session server-side after products/prices
      are finalized.

POST /api/billing/portal
  Purpose:
    - Create or redirect to the Dodo customer portal for active customers.

POST /api/webhooks/dodo
  Purpose:
    - Verify Dodo webhook signatures.
    - Process subscription lifecycle events idempotently.
    - Update local subscription state.


Database Schema Plan
====================

Use Supabase migrations when the project is connected. Do not hand-edit
production tables casually from the dashboard.

1. public.profiles
   Purpose:
     - App profile linked to auth.users.

   Columns:
     - id uuid primary key references auth.users(id) on delete cascade
     - email text not null
     - full_name text
     - avatar_url text
     - dodo_customer_id text unique
     - account_status text not null default "active"
     - created_at timestamptz default now()
     - updated_at timestamptz default now()

2. public.subscriptions
   Purpose:
     - Local mirror of Dodo subscription state.

   Columns:
     - id uuid primary key default gen_random_uuid()
     - user_id uuid not null references auth.users(id) on delete cascade
     - dodo_subscription_id text unique not null
     - dodo_customer_id text
     - dodo_product_id text
     - plan_key text not null
     - status text not null
     - current_period_start timestamptz
     - current_period_end timestamptz
     - cancel_at_period_end boolean default false
     - cancelled_at timestamptz
     - raw_payload jsonb
     - created_at timestamptz default now()
     - updated_at timestamptz default now()

3. public.checkout_sessions
   Purpose:
     - Track Dodo checkout sessions created by the app.

   Columns:
     - id uuid primary key default gen_random_uuid()
     - user_id uuid not null references auth.users(id) on delete cascade
     - dodo_session_id text unique
     - plan_key text not null
     - dodo_product_id text not null
     - checkout_url text
     - status text not null default "created"
     - metadata jsonb
     - created_at timestamptz default now()
     - updated_at timestamptz default now()

4. public.export_attempts
   Purpose:
     - Track export authorization and quota usage without storing images.

   Columns:
     - id uuid primary key default gen_random_uuid()
     - user_id uuid not null references auth.users(id) on delete cascade
     - client_export_id text not null
     - entitlement text not null
     - action text not null
     - requested_scale integer not null
     - allowed_scale integer not null
     - requires_watermark boolean not null
     - used_feature_keys text[] default '{}'
     - blocked_feature_keys text[] default '{}'
     - status text not null default "prepared"
     - failure_code text
     - output_pixel_width integer
     - output_pixel_height integer
     - period_start date
     - period_end date
     - created_at timestamptz default now()
     - completed_at timestamptz

   Constraint:
     - unique(user_id, client_export_id)

5. public.export_usage_months
   Purpose:
     - Fast monthly quota lookup.

   Columns:
     - user_id uuid not null references auth.users(id) on delete cascade
     - period_start date not null
     - period_end date not null
     - free_watermarked_exports integer not null default 0
     - pro_exports integer not null default 0
     - updated_at timestamptz default now()
     - primary key(user_id, period_start)

6. public.dodo_webhook_events
   Purpose:
     - Idempotency and audit log for Dodo webhooks.

   Columns:
     - webhook_id text primary key
     - event_type text not null
     - dodo_object_id text
     - processing_status text not null
     - payload jsonb not null
     - error_message text
     - received_at timestamptz default now()
     - processed_at timestamptz

7. public.limited_offer_slots, optional
   Purpose:
     - Only add this if a 100-seat founder/promo offer is actually launched.

   Notes:
     - Do not create founder-slot complexity until the offer is real.
     - Pricing, duration, and eligibility are TBD.


RLS And Security Rules
======================

Rules:
  - Enable RLS on every public table.
  - Client can read only its own rows.
  - Client cannot directly update billing state, quota, subscriptions, webhook
    events, or limited offer slots.
  - Server route handlers use service role only when needed.
  - Never expose SUPABASE_SERVICE_ROLE_KEY in browser code.
  - Never put billing authorization in raw_user_meta_data.
  - Prefer server-side database lookup of subscription status over stale JWT
    claims for launch.

Suggested policies:
  - profiles select: auth.uid() = id
  - profiles update: auth.uid() = id for safe profile fields only
  - subscriptions select: auth.uid() = user_id
  - checkout_sessions select: auth.uid() = user_id
  - export_attempts select: auth.uid() = user_id
  - export_usage_months select: auth.uid() = user_id
  - No client insert/update/delete policies for billing, quota, webhook, or
    payment-owned tables.
